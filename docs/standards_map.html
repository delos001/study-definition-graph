How the pinned standards fit together

Four bodies of guidance sit in data/raw/. This is what feeds what, and which of those connections has actually been checked against the files rather than assumed.

What was checked, and how

ConnectionStatusEvidence
USDM_UML.xmi generates the two UML files checked CDISC's own build script fires whenever that one file changes, and runs a dictionary generator against it.
USDM_CT.xlsx supplies the code lists checked All 517 codes named in the data dictionary appear in the terminology file. None missing.
Conformance rules check against the API file checked The rules say so in their own text: "must conform with the USDM schema based on the API specification."
ICH E9(R1) defines what USDM's estimand holds checked All four attributes E9(R1) names, plus intercurrent events, appear one-for-one on USDM's estimand class.
The two crosswalks run into USDM checked Both spreadsheets are laid out as two column groups: the other standard on the left, USDM on the right.
M11 and USDM share a code system checked Both use NCI codes, but they overlap only partly: 43 codes in common out of 407 in M11 and 634 in USDM. Not interchangeable.
Protocol becomes spreadsheet becomes JSON checked All three of CDISC's worked examples exist in exactly those three forms.
USDM_API.json is derived from the master not checked The class counts line up exactly (80 real classes, the 6 abstract ones dropped), so it plainly comes from the model. But the build script I read does not produce it, so how it is made is unconfirmed.
USDM draws on BRIDG, feeds SDTM not checked The implementation guide says both. Neither has been traced to a file.

The one thing worth knowing

The single most useful fact on this page: only one USDM file is authored by hand. Everything else machine-readable is generated from it. That means a disagreement between two of those files is not two opinions to weigh, it is a generation artifact, and the master wins.

That already resolved one open question. Three files appeared to disagree about how many classes USDM has. They do not. The master has 86, six of which are abstract scaffolding that never appears in real data, and two of which are an extension mechanism the documentation deliberately leaves out. Which is how you get 86, 84, and 80 from one model.
